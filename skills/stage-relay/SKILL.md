---
name: stage-relay
description: Open Stage Relay and bring the user's current task into its confirmation panel; reuse caller plans for execution.
---

On explicit plugin invocation or a request for its interface, call `relay_open_panel` first. Open the returned URL in the client's browser panel (in Codex use `open_in_codex` with a browser target). If that client has no browser panel, pass `open_browser=true` to use the system browser. A bare invocation completes when the GUI is visible; opening and viewing never starts models. A healthy panel with the same config, projects and version is reused (about 10–30 ms); a missing or dead record starts a new one (about 0.3 s). If the result contains `reconnect_required`, tell the user to reconnect the plugin so an older panel process is not kept side by side. A model-free shortcut (打开面板.cmd on Windows) is written under the runs root; never register autostart. The user can choose models/interfaces and click Start for planner → worker, or reuse an existing plan for worker only. If this session still exposes only the old three tools, run the command and arguments in this installed plugin's `.mcp.json` with `--open-panel` appended, then open its returned URL. Refresh/restart the plugin connection to load the new tool.

When an invocation includes a task, prepare it in this conversation and call `relay_prepare` with the project, original user_request and concise plan before finishing. Bring the task directly to the panel; do not ask the user to type it again, copy it out of the panel, or manually read the plan back in. Open the panel URL with `?draft=<draft_id>` after preparation so an existing tab loads the new task immediately. A visible panel also reads changed drafts locally, preserving additions when the same task's plan changes and clearing old additions when a new task arrives. The user reviews the task and changes it through the optional supplement box. Preparation never starts models. Start launches the execution model; the answer then offers user confirmation or original-planner review. If the tool is not loaded yet, write its JSON arguments to a workspace file and run the installed `.mcp.json` command and arguments with `--prepare-plan <file>` appended. A browser page cannot wake this conversation automatically; task-bearing invocations already contain the instructions needed to prepare the draft. API planner mode remains an explicit alternative. If the user explicitly authorizes starting execution in the conversation, use relay_submit with user_request and review_mode=user_choice unless automatic review was requested; respect any explicit prepare-only instruction.

When preparing a draft, include `user_request` with the user's original task from this conversation and `instructions` with the confirmed requirements relevant to it. They are saved locally for automatic display; instructions also join the worker's constraints. Do not copy unrelated chat history or read other conversations. The panel asks for additions without requiring the user to repeat existing instructions. Older drafts without these fields display their saved goal as a summary.

Keep invocation workflow instructions out of the worker's constraints. In particular, honor “prepare only / 暂不执行” by saving a draft and not submitting a job; do not turn that pause into a requirement forbidding the worker from executing after the user clicks Start. Only actual task requirements belong in instructions/constraints. Confirmation supplements join the saved plan and are also passed explicitly with the original task to the worker; later adjustments override conflicting plan details without discarding unrelated requirements.

When asked to delegate a task, reuse the calling agent's planning. Send a concise `relay_submit` handoff: goal, relevant files and code facts, actionable steps, and any decisions or constraints. Omitted decisions default to following the supplied steps; IDs are assigned D1… for decisions, S1… for steps and C1… for constraints. Acceptance commands come from local configuration.

Choose a stable task_key. Resubmitting the same project/key/plan returns the saved job; a different plan requires a new key or an explicit resume. Target a clean, committed Git repository inside the configured roots. While it runs, leave that repository to the worker.

Use `relay_wait` with a long local wait (up to 50 seconds). Pass the last revision to suppress repeated results. Waiting and viewing the panel only read local files. Use full_result=true when the changed-file preview is insufficient or marked details_truncated; it returns the complete stored result without another model call. Blockers, evidence, residual issues and check conclusions are preserved in the default return. Check log paths expose the full saved logs when tails are insufficient.

After execution the user can confirm the answer themselves, choose the current Codex conversation to review, or select an already saved model in the panel. Selecting a model reuses its existing interface and credentials; reading the saved list makes no model request. Only the user's explicit review action starts that model's read-only audit, which can incur provider usage. It preserves the original planning/execution configuration and does not repeat execution or tests. A matching saved model/interface/result review is reused. Explicit automatic-review callers/CLI configurations retain their original-planner review behavior; reviews do not start a correction loop.

When the user sends a task back to this Codex conversation for review, read the saved plan, full result, checks and diff, and relevant project files when needed. This works for caller-planned and API-planned tasks. Use `relay_record_review` with job_id, result_revision=review_revision from relay_wait, and review {status, summary, evidence, issues}. Status is approved, changes_requested, or unable_to_verify. State what was actually verified; a response-only task need not have automated project tests. Do not invent a review, silently rerun execution, or invoke a separate model. If the tool is not loaded, write its arguments to a workspace JSON file and use the installed `.mcp.json` command/arguments with `--record-review <file>`. The browser cannot wake this conversation; the user copies its review request here. Reviews and user confirmations are bound to the saved result version and become stale after execution or check evidence changes. User confirmation is distinct from model review and does not mark unrun tests passed.

Review worker residual notices individually. Give concrete verification steps and expected results for open issues. Put the zero-based indexes of notices actually resolved or confirmed outside this task's scope in review.resolved_residual, with verification evidence; those move to the panel's reviewed history and leave the issue count. Do not clear unresolved notices or claim unrun tests passed. Saving a new review replaces the prior conclusion for the same saved result; it does not run tests or repair files.

For `awaiting_plan`, resolve the named decision and use `relay_resume` with a revised concise plan. For interrupted work, inspect partial changes before setting retry_interrupted. Request budgets remain cumulative. Completed jobs are returned without rerunning. `needs_manual_verification` means no acceptance checks were configured.

Model checks are user actions in the panel: interface/catalog (no generation), minimal generation, and relay compatibility (real Codex → gateway → model → local JSON validation in a temporary read-only sample). Never trigger them from opening, refreshing, submitting or waiting, and never sweep all models. A compatibility record only says the link worked when tested; after an endpoint, model or credential change it is marked stale.

Inherit the operator's execution settings and tools. Preserve necessary facts and evidence; token savings come from reusing work, idempotent submission and on-demand retrieval, not shortened model output, fewer allowed repairs or disabled tools.

Task submission and recovery can incur configured provider usage and edit project files. Keep the caller's original authorization and configured approval controls. Report measured usage or unknown values; do not promise a savings percentage. For installation or provider setup, read [the setup reference](references/setup.md).

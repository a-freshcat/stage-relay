---
name: stage-relay
description: Open Stage Relay with the user's task and prepare the current Codex plan for confirmation before execution.
---

For a bare plugin invocation or interface request, call relay_open_panel without a task. Open its URL in the client's browser panel (Codex: open_in_codex, browser target), or use open_browser=true if no panel exists. Opening never starts models. A healthy matching service is reused; a model-free Windows shortcut is provided, without autostart. If reconnect_required is returned, explain that the plugin connection must refresh to load the current version.

When invocation includes a task, FIRST call relay_open_panel with its exact user_request. Specify project for an existing repository; for a standalone drawing/document/new artifact, OMIT project and use the isolated committed task project returned in task.project. Open the URL, then continue planning in the SAME turn as the current Codex. Read only the relevant facts, prepare actionable steps and requirements, and call relay_prepare with task.project, task.invocation_id and the original user_request. For a new output, use generated README.md as the facts anchor and name future output paths in steps. End the turn once the plan is saved and ready for confirmation; do not require another message to begin planning. If the user explicitly requests opening only or delaying planning, honor that pause.

Planning ends at the saved plan, not a finished deliverable. Keep existing project files unchanged, leave implementation commands and deliverable generation to the worker, and do not call relay_submit during preparation. Execution starts only when the user clicks Start or separately authorizes it. User supplements are optional and do not block a ready plan from starting.

Opening and saving the plan make no extra model calls. The panel automatically reads the original task, then the saved plan and enables Start; failure shows the current error without reviving an older plan. Preserve additions for the same task, clear them for new tasks, and do not ask the user to retype the invocation or refresh the page. If tools lack task-aware arguments, save the same JSON arguments, invoke the CURRENT installed .mcp.json command/args plus --open-task <file>, open the URL, then prepare and save via --prepare-plan <file> in the SAME turn. Refresh the plugin connection for updated tools. API planning remains an explicit alternative.

When preparing or updating a draft, include `user_request` with the user's original task and `instructions` with actual task requirements, including later refinements. They are saved locally for automatic display; instructions also join the worker's constraints. Do not copy unrelated chat history or read other conversations. Older drafts without these fields display their saved goal as a summary.

Keep invocation workflow instructions out of the worker's constraints. In particular, honor “prepare only / 暂不执行” by saving a draft and not submitting a job; do not turn that pause into a requirement forbidding the worker from executing after the user clicks Start. Only actual task requirements belong in instructions/constraints. Confirmation supplements join the saved plan and are also passed explicitly with the original task to the worker; later adjustments override conflicting plan details without discarding unrelated requirements.

When the user separately authorizes execution, reuse the calling agent's planning. Send a concise `relay_submit` handoff: goal, relevant files and code facts, actionable steps, and any decisions or constraints. A task-bearing invocation, a request to open/refine/prepare, or an open panel alone is not execution authorization. Omitted decisions default to following the supplied steps; IDs are assigned D1… for decisions, S1… for steps and C1… for constraints. Acceptance commands come from local configuration.

Choose a stable task_key. Resubmitting the same project/key/plan returns the saved job; a different plan requires a new key or an explicit resume. Target a clean, committed Git repository inside the configured roots. While it runs, leave that repository to the worker.

Use `relay_wait` with a long local wait (up to 50 seconds). Pass the last revision to suppress repeated results. Waiting and viewing the panel only read local files. Use full_result=true when the changed-file preview is insufficient or marked details_truncated; it returns the complete stored result without another model call. Blockers, evidence, residual issues and check conclusions are preserved in the default return. Check log paths expose the full saved logs when tails are insufficient.

After execution the user can confirm the answer, choose this Codex conversation to review, or select a saved model. The panel defaults to auto-correction after rejection, with a review-only opt-out and billing explanation. API reviewers run read-only; changes_requested sends concrete feedback to the original worker, runs configured checks and returns to the SAME reviewer. No extra planner is launched. Model/interface/result-matched reviews are reused; upgrading alone never restarts old tasks. CLI review_corrections=false selects review-only behavior.

When the user sends a task back here for review, read its saved plan, full result, checks, diff and relevant files. Call relay_record_review with job_id, the CURRENT result_revision and review {status, summary, evidence, issues, change_requests?, resolved_residual?}, honoring the requested auto_correct boolean (default true). Rejection with auto-correction requires change_requests [{path, location, problem, requested_change, verification}]; give a concrete verification method and expected outcome, using empty path/location for response-only tasks. Do not invent locations, commands or test results. Status is approved, changes_requested or unable_to_verify. Approval and insufficient-evidence records do not launch a worker; automatic rejection can incur worker usage and edit the project.

If relay_record_review returns queued, use relay_wait, then inspect the NEW result/version, checks and diff and review it yourself in THIS conversation. Continue until approved, blocked, insufficient evidence or paused; do not repeat task submission, reuse old revisions, or call another reviewer model. The browser cannot wake a conversation after its turn ends; the panel offers a request to return the latest result here. If loaded tools lack the new fields, invoke the CURRENT installed .mcp.json command/arguments with --record-review <JSON arguments file>. In this fallback, also wait through that SAME command/arguments plus --wait-job <job_id> --seconds 50 --full-result; old tools may calculate outdated result versions. Reconnect the plugin to load updated tools. Every worker result gets a new version, even for identical answer text; confirmation remains distinct from passed tests.

Review worker residual notices individually. Give concrete verification steps and expected results for open issues. Put the zero-based indexes actually resolved or confirmed outside scope in review.resolved_residual, with evidence. Unresolved notices stay open; failed/unrun tests stay failed/unrun. Current and historical reviews and correction rounds remain available. A repeated rejection without changed files, answer or check evidence pauses automatic correction. Use relay_pause_corrections for a boundary pause; the current stage may finish and be billed. Inspect saved feedback and edits before an explicitly authorized relay_correct continuation. User confirmation ends the cycle. Existing budgets remain cumulative; no extra hard round/output cap is added.

For `awaiting_plan`, resolve the named decision and use `relay_resume` with a revised concise plan. For interrupted work, inspect partial changes before setting retry_interrupted. Request budgets remain cumulative. Completed jobs are returned without rerunning. `needs_manual_verification` means no acceptance checks were configured.

Model checks are user actions in the panel: interface/catalog (no generation), minimal generation, and relay compatibility (real Codex → gateway → model → local JSON validation in a temporary read-only sample). Never trigger them from opening, refreshing, submitting or waiting, and never sweep all models. A compatibility record only says the link worked when tested; after an endpoint, model or credential change it is marked stale.

Inherit the operator's execution settings and tools. Preserve necessary facts and evidence; token savings come from reusing work, idempotent submission and on-demand retrieval, not shortened model output, fewer allowed repairs or disabled tools.

Execution subagents are optional and off by default. The panel offers off, auto and manual assignments; relay_submit accepts subagents {mode: off|auto|manual, max_concurrent?: integer, tasks?: [{goal, access: read|write, files: [project-relative paths]}]}. Only include tasks in manual mode, with disjoint write sets. Preserve the caller plan; do not call another planner to arrange delegation. Native children inherit the execution model/provider, permissions and reasoning settings. Do not promise file-level isolation or guaranteed savings. A child answer is evidence for the execution parent to integrate, not final user approval. Missing closure or incomplete collaboration blocks acceptance; inspect saved changes before recovery. relay_wait returns compact child status, full_result=true includes saved child answers. Routed Responses usage includes parent and child requests and must not be added to CLI parent usage; absent usage and price remain unknown.

Task submission and recovery can incur configured provider usage and edit project files. Keep the caller's original authorization and configured approval controls. Report measured usage or unknown values; do not promise a savings percentage. For installation or provider setup, read [the setup reference](references/setup.md).

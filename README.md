# Stage Relay 0.1.1 · 多 Agent 协作台（Codex + DSH）

由你指定成员和职责，面板把工作交给原应用中的真实 Agent 执行。Codex 与 DSH 的原生任务组协作已实际验证；面板不直接调用模型 API，也不替 Agent 决定结论。

这是 0.1.x 全新版本线：仓库主线的旧版（1.4.0 系列的「模型阶段接力」插件）已保留为独立分支，与当前结构不兼容，不在此目录内。0.1.1 相对 0.1.0 只做上下文增长优化，不改变协作语义。

## 能力概览

- **项目与分工**：一个任务指定方案监督、执行、汇总负责人；可添加同应用多个成员，也允许一人兼任多职责。
- **项目级群聊**：每个任务一条群聊线程，没有议题也能交接。消息进入其他成员信箱，成员需主动读取才能响应；成员连续发言 4 条后等待用户回复。
- **原生会话绑定**：登记来源（面板创建 / 用户绑定）、会话 ID 与绑定轮次。成员卡固定显示「绑定会话 + 轮次 + 忙碌状态」，明确它不是你可能正在看的那个窗口。
- **增量唤醒与按需读取**：唤醒只带本次事件、相关对象和项目概要；已验收板块、已解决议题与群聊历史折叠为计数，需要时用 `relay_project` / `relay_task` / `relay_issue` / `relay_event` 读全文。后台轮询按持久化游标只扫新事件。固定协作规则每个绑定轮次完整下发一次，其余唤醒只带摘要，`relay_rules` 随时返回原文。
- **结束与清理**：结束任务与「已生成汇总」是两件事；结束时停止派发、撤销未完成板块、按来源归档或解绑会话，并提供固定规则的清理预览与可恢复移动。
- **设置与占用**：按项目显示本应用登记的附件、临时目录与可恢复区容量，提供清理预览与恢复入口；工作区不计入、不扫描。
- **项目回收区**：项目可「移入回收区」并逐条「移回列表」，工作区文件始终不动。

## 从源码启动

需要 Python 3.11 或更新版本，无需第三方依赖。

双击根目录的 **启动 Stage Relay.cmd**，或运行：

```powershell
python app.py --open
```

默认地址为 [本地面板](http://127.0.0.1:4318)。数据保存在根目录的 `data/`，只监听本机；重复运行会复用已启动的服务。

## 打包 Windows 桌面版

```powershell
python build_desktop.py
```

输出到 `release/StageRelay-<版本>-codex-dsh/`，生成带独立窗口的 `Stage Relay.exe`、协作桥 `StageRelayBridge.exe` 和随附运行环境，目标机器不需要安装 Python。桌面窗口使用 Microsoft WebView2 Runtime。`release/`、`build/` 与本机 `data/` 都不入库。

## 建立自己的任务

1. 新建任务，填写目标，选择或新建工作区文件夹，再指定方案监督、执行、汇总负责人。
2. 添加工作板块，指定负责人并填写验收条件，然后派发。
3. 在成员卡把原应用会话绑定到该职责；成员自己读取信箱、执行并汇报。
4. 执行结果由监督者独立核验；核验通过后再派发汇总。
5. 任务完成后「结束任务」；需要从列表移除时再「移入回收区」，随时可移回。

## 上下文增长与按需读取

长期项目里，真正会膨胀的是「每次唤醒都重发整份项目」。Stage Relay 的处理方式：

- **唤醒**只包含本次事件（seq、kind、actor、摘要）、它引用的板块或议题、绑定轮次与规则版本，以及不含已完成证据的项目概要。`report` / `review` 得到的证据预览更长（1200 字），但仍会标明原文长度与取全文的工具，不冒充完整依据。
- **已完成与已解决**的板块、议题和群聊历史折叠为计数；开放板块与开放议题列表也各有上限，超出部分用计数说明。全文用 `relay_list` 分页读取或按对象直取。
- **`relay_inbox`** 默认从上次读取位置继续；传 `full=true`（或 `after=0`）会从头分页重读事件日志——注意它只扩大事件范围，证据仍是摘要，完整正文靠 `read_*`。
- **游标消费**：读取被记为「待确认」，下一次调用才推进。响应没送到调用方时宁可重发一次，也不会静默吞掉通知；读取不等于执行。
- **暂缓不阻塞**：达到自主讨论上限的事件进入持久 `deferred` 集合，之后每次轮询重试，用户发言解锁后补送；它只推迟自己，同项目其他议题与新派发照常送达。
- **合并**只并事件 ID 并持久化；第二轮合并与第一轮取并集，不覆盖已并入的 ID；被回收的成员从合并中被剔除，若头部被回收而其余事件仍有效，它们会各自恢复为独立派发，不会随之丢失。
- **按需读取**提供 `relay_project`、`relay_task`、`relay_issue`、`relay_message`、`relay_event`、`relay_list` 与 `relay_rules`，读取前校验成员是否属于该项目；证据、决定与附件名原样返回，`relay_list` 分页并给出 `total` / `next_offset`，按路径自下而上取一条不需要读整个项目。
- **规则恢复**：完整协作规则每个绑定轮次下发一次，之后只带摘要；换绑、会话重建或长时间静默后会重新下发，`relay_rules` 总能拿到原文。
- **旧队列迁移**：升级时把尚未送达的旧式大提示原地改写为轻量体，保留 job 与事件唯一键、保留已并入的事件 ID；已送达、在途与不确定的记录不动，重复启动幂等。

实测（`qa/context_measure.py`，同一测量脚本分别跑提交前源码与当前源码）：

| 场景 | 单次唤醒正文 | `relay_inbox` 项目部分 | 空闲轮询中位数 |
| --- | --- | --- | --- |
| 小项目（1 板块） | 123,473 → 3,574 字节 | 122,608 → 2,196 字节 | 9.9 → 6.5 ms |
| 长期项目（25 板块 / 8 议题 / 40 条群聊） | 279,338 → 3,578 字节 | 278,473 → 2,199 字节 | 170.2 → 9.0 ms |

唤醒大小基本不再随项目历史增长：长期项目与小项目只差 4 字节，因为随唤醒发送的只有本次事件和仍开放工作的上限列表。字节是该机器上序列化后的实际长度；Token 数取决于分词器，这里不做换算，也不宣称节省比例。原生会话自身的历史增长由 DSH 自带的 `dsh-compaction-basic` 与 `/compact` 处理，Stage Relay 不模拟也不截断它。

## 结束任务与清理的边界

结束按钮先二次确认并填写保留期（1-365 天），然后：

1. 置为只读，停止派发，把未完成的板块标为「已撤销」，取消尚未送达的原生任务。
2. 只处理登记过的资源：面板创建的会话请求原应用 `workspaceRegistry.archiveSession(sessionId,{stopActivity:true})` 归档；用户手动绑定的会话只解除绑定。
3. 共享应用、插件、接入配置与工作区一律保留，不按进程名关闭进程，不删除原应用数据库。
4. 清理只按固定规则列候选（本应用为此项目创建的 `tmp/<project_id>`、已无引用且超保留期的上传附件、已删除项目的孤儿附件与过期计划）。执行时移入 `recovery/` 并写 `manifest.json`，原子落盘、可恢复；失败项保留原位，重复运行不扩大范围。

## 如实说明的限制

- 插件侧的归档调用已实现，但当前安装的 DSH 版本是否向插件暴露 `workspaceRegistry` 尚未做端到端验证；未暴露时回执失败并保留待重试，不会静默当作已归档。
- DSH 插件接口不提供原生子会话的父子关系，因此只登记面板实际创建的会话；原生 `turnId` 也无法取得，执行记录显示为未知，只用 jobId / 事件序号 / 绑定轮次关联。
- Antigravity 尚不支持原生唤醒。
